# Design: a Roc platform of liton's own

The design behind [own-platform-plan.md](own-platform-plan.md). Nothing here is
built. Claims about Roc and basic-webserver cite their source. Anything marked
*(unverified)* is inferred and must be checked in the spike before anyone relies
on it.

## Architecture

Two halves, like any Roc platform on the new compiler: Roc modules giving the
app contract and typed effects, and a Zig host that runs the app. The platform
lives in liton's repository (`platform/`). `zig build` compiles the host from
source with the pinned Zig and Roc, so liton never waits for a release.

### Host ↔ Roc ABI

The new compiler uses a direct-symbol ABI. A platform's `main.roc` names the
entry points the app gives the host (`provides`) and the effects the host gives
the app (`hosted`). Both are plain C-ABI linker symbols. Compiled Roc calls
`roc_alloc`, `roc_dealloc`, `roc_realloc`, `roc_dbg`, `roc_expect_failed` and
`roc_crashed`, which the host exports
([basic-webserver `platform/main.roc`](https://github.com/roc-lang/basic-webserver/blob/main/platform/main.roc),
the "Runtime Symbols" in its generated `src/roc_platform_abi.rs`). Hosted
functions own their refcounted arguments and must release them. Results pass
one owned reference to Roc.

liton follows three rules from the platforms it has seen:

- **A narrow surface.** roc-signals' Wasm host passes only `List(U8)`, an opaque
  `Box` and integers, with hand-written `extern struct`s (`platform/host/host.zig`
  in 0.5.0). basic-webserver passes rich records through about 15,000 lines of
  generated Rust glue. liton passes bytes, `Str`, integers, `Box`es and a few
  flat records, through Zig glue generated by `roc glue` and checked in, as
  kai's platform does.
- **Ownership moves between threads. It is never shared.** Compiled Roc's
  refcounts are atomic unless the compiler proves an allocation is
  thread-local (`RC_TYPE: Refcount = .atomic` in Roc's
  `src/builtins/utils.zig`). That makes concurrent handlers sound, which
  basic-webserver depends on. Still, the host never touches the refcount of a
  value a Roc thread may still hold. Buffers the I/O thread has finished with
  go back on a release queue, and a Roc thread decrements them between calls.
- **A crash ends the process.** `roc_crashed` must not return (generated glue,
  and roc-signals' `spec.zig`, which exits). So a panic in any handler or
  process step stops the daemon, and the service manager restarts it. Processes
  must rebuild from SQLite when they start. Recovering in-process, for example
  by `longjmp` out of `roc_crashed`, would leak and corrupt refcounts, and is
  out of scope.

Entry points (`provides`): `roc_init`, `roc_respond`, `roc_step`, `roc_then`
(an `Ask`'s continuation), `roc_render` (a live query's rows), `roc_shutdown`,
plus `roc_drop_*` for each kind of retained value. Hosted effects mirror
basic-webserver's names where they overlap (`sqlite_*`, `tcp_*`,
`http_send_request`, `env_var`, `stderr_line`, `unix_time_now`), so porting the
daemon changes imports, not logic.

### I/O model

There are three kinds of thread, and no async runtime:

| Thread | Owns | Runs |
|---|---|---|
| I/O loop (1) | every socket, timers, SSE subscribers, process connections | epoll; HTTP/1.1 parsing; WebSocket and SSE framing; budgets |
| Process runner (1) | every process's state | `roc_step`, one event at a time, in one total order |
| Handler pool (N, default 2) | nothing between calls | `roc_respond` and `roc_then`, synchronously, with blocking local effects |

- **epoll, not io_uring.** A personal daemon serves a few dozen sockets, so
  epoll's cost is noise. io_uring is blocked by Docker's default seccomp
  profile and disabled on some hardened kernels *(unverified, reported)*.
  The loop sits behind a small interface, so macOS can add kqueue in M4. Zig
  0.16's `std.Io` may provide this abstraction *(unverified: check in the
  spike, and adopt it if it is stable)*.
- **Handlers block, processes don't.** A handler runs on a pool thread and may
  call blocking effects (`Sqlite.query!`, outbound `Http.send!`, and, for
  parity only, `Tcp`), as basic-webserver's
  bounded executor allows (`src/roc_executor.rs`). A process step is a pure
  function. Its I/O is data that the loop performs, and the results return as
  events. A slow upstream can then stall only handlers that chose to call it.
- **Backpressure everywhere, all bounded.** Each process has a bounded mailbox.
  Above its high-water mark the loop stops reading that process's sockets, so
  TCP pushes back on Paseo, and `Process.tell!` returns `MailboxFull`. Accepted
  connections and queued requests have caps, and requests beyond them get
  `503`. Each SSE subscriber has a bounded send buffer. A subscriber that
  overflows it is closed, and it resumes with `Last-Event-ID`. The host times
  every step and handler, and traces any that take over 50 ms.

### Modules and their signatures

Sketched in the new compiler's syntax. Names may change, but the shapes are the
design.

```roc
platform "liton-server"
	requires {
		# Three type variables in `requires` is unverified; the fallback is
		# messages as JSON `Str`.
		[Context : context, Proc : proc, Msg : msg] for program : {
			init! : () => Try({ config : Server.Config, context : context, processes : List(Process.Spec(proc)) }, [Exit(I64), ..]),
			respond! : Http.Request, context => Try(Http.Outcome(msg), [ServerErr(Str), ..]),
			step : proc, Process.Event(msg) -> Process.Step(proc, msg),
			shutdown! : context => {},
		}
	}
```

`step` is `->`, not `=>`. The type checker therefore guarantees that a process
performs no effects, which no review can promise.

```roc
# Http (server): basic-webserver's request type, so handler code ports as is.
Outcome(msg) : [
	Respond(Response),
	Subscribe(Push.Subscription),  # the host owns the stream from here on
	Ask({ to : Str, question : msg, timeout_ms : U64, then : Try(msg, [Timeout, NoProcess, MailboxFull]) -> Response }),
]

# Process
Spec(proc) : { name : Str, initial : proc, restart : [Never, Backoff({ first_ms : U64, max_ms : U64 })] }
Frame : [Text(Str), Binary(List(U8))]
Event(msg) : [
	Started,
	Told(msg),
	Asked({ question : msg, reply_to : ReplyTo }),
	Timer(Str),
	Connected(Str), Received(Str, Frame), Disconnected(Str, Str),   # by connection name
	Answered(Str, Try(Http.Response, Http.Err)),                   # by request tag
	Wrote(Str, Try({}, Sqlite.Err)),
	Watched(Str), Unwatched(Str),                                  # a topic's first subscriber came / last left
	OverBudget(Str, Budget.Refusal),
]
Effect(msg) : [
	Connect({ name : Str, upstream : Str, as : [WebSocket({ path : Str, protocols : List(Str) }), Raw] }),
	Send(Str, Frame), Close(Str),
	Http({ tag : Str, upstream : Str, request : Http.Request }),
	After({ ms : U64, timer : Str }), Cancel(Str),
	Tell(Str, msg), Reply(ReplyTo, msg),
	Write({ tag : Str, statements : List(Sqlite.Statement) }),   # one transaction
	Publish({ topic : Str, id : U64, data : Str }),
	Log(Str),
]
Step(proc, msg) : { next : [Continue(proc), Stop([Done, Failed(Str)])], effects : List(Effect(msg)) }
tell! : Str, msg => Try({}, [NoProcess, MailboxFull])          # from handlers

# Push (SSE): topics are declared by prefix in Server.Config.
TopicKind : [Log({ keep : U64 }), Latest]   # replay the last `keep` events, or only the newest
Subscription : { topics : List(Str), after : List({ topic : Str, id : U64 }) }

# Sqlite: basic-webserver's API (open!, query!, query_many!, execute!, begin!),
# with a RowEncoding that implements the whole parser protocol, plus:
Statement : { query : Str, params : List((Str, Value)) }
live! : Db, { topic : Str, query : Str, params : List((Str, Value)) } => Try({}, LiveErr)

# Budget: declared in Server.Config, enforced by the host.
Upstream : { name : Str, host : Str, port : U16, connections : U64, in_flight : U64, min_interval_ms : U64 }
Refusal : [Undeclared, TooManyConnections, TooSoon({ retry_in_ms : U64 }), Saturated]

# Assets: served by the host, at build-time hashed URLs.
url : Str -> Str            # "app.wasm" -> "/ui/app.3f9c2a1e.wasm"

# Trace
note! : Str => {}           # adds a mark to the current step's or handler's span
```

Outbound `Http`, `Tcp`, `Env`, `Stderr` and `UnixTime` keep basic-webserver's
signatures for handlers.

## The process model

A process is a named, long-lived, pure state machine owned by the host. It is
the shape liton's providers already have: an event comes in, and a new state
and a list of effects come out (design.md, "Providers").

- **Declared** in `init!` as a `Spec`: a name, an initial state and a restart
  policy. The app has a single `proc` tag union holding each process's state
  type, `[PaseoLink(PaseoLink.State), MockClock(MockClock.State)]`, and `step`
  dispatches on it. `init!` is effectful, so it can read SQLite to build an
  initial state.
- **Spawned** by the host after `init!` succeeds, each with a `Started` event.
  The host holds each state as a `Box(proc)`. A step consumes the box and
  returns the next one, so the state has one owner and Roc can update it in
  place.
- **Receives** events in mailbox order, one at a time, on the process runner.
  Events are messages (`Told`, `Asked`), timers, its own connections' frames,
  its effects' results (`Answered`, `Wrote`), and subscriber changes on topics
  it publishes (`Watched`, `Unwatched`).
- **Requests effects** by returning them. The host performs them in list order
  and reports each result as a later event. Each connection and timer belongs to
  one process. When a process stops, the host closes its connections and
  cancels its timers.
- **Supervised** by its `restart` policy. After a `Stop(Failed(why))`, the host
  waits for the backoff (doubling from `first_ms` to `max_ms`, reset after a
  minute without failure), then starts the process again from its `initial`
  state with `Started`. A lost connection is not a failure: the process sees
  `Disconnected` and decides for itself. A Roc crash ends the daemon (see
  "Host ↔ Roc ABI").
- **Talks to handlers** in three ways. A handler can `Process.tell!` a message
  without waiting. It can return `Ask`: the host delivers `Asked` with a
  `reply_to`, and when the process returns `Reply`, the host calls `then` with
  the reply on a handler thread, under a timeout. And it can read what the
  process wrote to SQLite. `then` is a closure the host retains across threads,
  as basic-webserver retains SSE sources (`roc_sse_advance_for_host` takes a
  `RocErasedCallable`).

### Example: the Paseo link

```roc
PaseoLink.State : {
	link : [Down({ attempts : U64 }), Connecting, Up],
	sessions : Dict(Str, Paseo.State),   # each session's timeline state (today's Paseo.State)
	watched : Set(Str),                  # topics with subscribers
	asks : Dict(Str, ReplyTo),           # MCP calls in flight, by tag
}
```

| Event | Effects |
|---|---|
| `Started`, or `Timer("reconnect")` | `Connect({ name: "paseo", upstream: "paseo", as: WebSocket({ path: "/ws", protocols: ["paseo.bearer.…"] }) })` |
| `Connected("paseo")` | `Send` hello (`Paseo.hello`), then the agent and workspace listings, and a subscription for each watched session *(Paseo's subscribe messages, behind `explicit_event_subscriptions`, still to be read from its client)* |
| `Received("paseo", Text(json))` | decode with today's `Paseo.*`, `PaseoWorkspaces.*` and `PaseoGit.*` answers, then `Paseo.update`. `Write` new entries and states, `Publish` to `timeline/<id>`, `sessions`, `workspaces` |
| `Watched("timeline/<id>")` | add to `watched` and, if `Up`, `Send` a timeline request and a subscription. `Unwatched` sends the reverse |
| `Watched("git/<dir>")` | `After({ ms: 0, timer: "git/<dir>" })`. Each `Timer` asks for status, and diffs when `PaseoGit.refresh` says so, then arms the next timer while the topic is watched |
| `Asked({ question: SendPrompt(…), reply_to })` | `Http({ tag, upstream: "paseo-mcp", request: Paseo.send_prompt(…) })`, keeping `reply_to` in `asks` |
| `Answered(tag, result)` | `Reply(reply_to, Accepted)` or `Rejected(reason)` |
| `Disconnected("paseo", why)` | `link: Down`, `Publish` to `status`, `After({ ms: backoff(attempts), timer: "reconnect" })` |

`Watched`/`Unwatched` replace today's `paseo_interests` table and its
10-second `interest_ms`. The single connection replaces the 3-second cycle,
`paseo_checks` and its lease. The pure code that decodes Paseo stays as it is.
The host does the WebSocket framing, so the daemon's `WebSocket.roc` and its
8-MiB read loop go away.

### The UI subscribing (idea 2)

1. Panes need topics: a chat pane needs `timeline/<session>`, the drawer
   `sessions` and `workspaces`, a Changes pane `git/<dir>`.
2. The UI holds one roc-signals `Port.subscription` (`liton/events`) whose
   argument is the tab's topic set and last seen ids, with `Every(256)`
   delivery. A few lines of JavaScript open an `EventSource` on `/api/events`
   and `emit` each event. When the set changes, `Engine.watch_latest` replaces
   the subscription and the old stream's `AbortSignal` closes it (roc-signals
   0.5.0 `platform/Port.roc`).
3. `respond!` authorizes and returns `Subscribe`. The host replays each topic
   after the given ids, then streams live events. No Roc runs per subscriber.
4. Event data are `capabilities/` types, applied with the functions that apply
   poll answers today (`Model.polled`, `Model.git_polled`). On `Closed` the UI
   falls back to polling, which stays through M2.

HTTP/1.1 browsers open at most six connections per origin, so a seventh tab on
a plain-HTTP daemon would stall. Behind Caddy over HTTP/2 the limit goes away.
Sharing one stream across tabs (a `SharedWorker`) is an open question.

## Budgets, assets, live queries, tracing, record and replay

**Upstream budgets (idea 3).** The app declares each upstream in
`Server.Config`. Paseo's WebSocket gets `connections: 1, min_interval_ms: 1000`
for reconnects. Paseo's MCP endpoint gets `in_flight: 4`. Every network effect
must name a declared upstream, and the host validates all of them before it
listens. A `Connect` or `Http` over budget is refused with `OverBudget`
(`TooSoon` says when to retry), and is never queued without bound. Handler-side
`Http.send!` names an upstream too. The host merges identical in-flight `GET`s
to the same upstream and counts every call per upstream for tracing. Caching
stays in SQLite, where it is visible.

**Assets (idea 4).** At build time `zig build` hashes each file in `zig-out/www`
and compresses it with gzip (Zig's std) and brotli (the `brotli` tool, build
time only). It writes a manifest and embeds it all in the host with
`@embedFile`. That works because liton builds its host from source. The host
serves `/ui/<name>.<hash>.<ext>` with `Cache-Control: public, max-age=31536000,
immutable`, choosing the encoding from `Accept-Encoding`, and serves
`index.html`, rewritten to the hashed names, with `no-cache`. A deploy is one
file. How far brotli shrinks the 10.8-MB wasm is to be measured.

**Live queries (idea 5, after M3).** `Sqlite.live!` registers a query under a
topic. When the query is prepared, SQLite's authorizer callback reports every
table it reads (`SQLITE_READ`). After a commit that touched one of those tables
(`sqlite3_update_hook` notes them, the commit hook fires), the host reruns the
query and calls `roc_render` to turn the rows into the topic's JSON. It
publishes the result only if its hash changed. The update hook does not fire for
`WITHOUT ROWID` tables or for some truncating deletes
([sqlite.org/c3ref/update_hook.html](https://sqlite.org/c3ref/update_hook.html)),
so liton must avoid both in live tables. This could later replace a process's
own `Publish`.

**Tracing (idea 9).** The host records a fixed-size span for every handler,
step and effect: who (route or process), what (effect kind, upstream), start,
duration, bytes and outcome. It keeps them in a ring buffer of 64k entries and
publishes per-upstream counts each second on a `trace` topic for a liton
widget. `Trace.note!` adds a mark. There is no sampling, since a span is a few
stores into the ring.

**Record and replay (idea 6).** Steps are pure and run in one total order, so a
log of process events (host bytes, before they become Roc values) rebuilds
every state exactly. `liton-daemon --replay <log>` feeds it to `roc_step`
without I/O and checks that each step returns the effects that were logged.
Handlers are not recorded, because their SQLite reads and clock would need
logging too. The log holds user data, so it is off by default and stays local.

## Compiler churn

liton already pins Roc (`.roc-version`). The platform adds:

- **Build from source with the pin.** The host builds with the app, in liton's
  repo, so a change a nightly needs lands in the same commit as the pin bump.
  liton waits for no platform release.
- **CI on two compilers.** The pinned nightly must pass `zig build test`, e2e
  and an example app. The newest nightly runs the same jobs daily and is
  allowed to fail. A failure is a note to read, not a broken build.
- **Glue checked, layouts asserted.** The generated Zig glue is committed. A
  `--check` step fails when it is stale, as basic-webserver's
  `scripts/regenerate_glue.py` does. `comptime` size and alignment asserts on
  every boundary type catch a layout change at build time, not as memory
  corruption. Keeping the surface narrow keeps this small.

What broke basic-webserver lately, and how this design absorbs it:

- **BUG-031:** from `nightly-2026-11-11-7679cc5`, every 0.21.0 app segfaults at
  startup. Since [roc-lang/roc#12949](https://github.com/roc-lang/roc/pull/12949)
  executables are static-pie, and static musl platforms must link `rcrt1.o`,
  not `crt1.o`. Here the platform links `rcrt1.o` from the start, as
  roc-signals 0.5.0 does. The next change of this kind would show up in the
  daily newest-nightly job, and the fix would be one line in liton's own repo.
- **BUG-032:** from `nightly-2026-11-10-f7d1f19`
  ([roc-lang/roc#12933](https://github.com/roc-lang/roc/pull/12933)), a parser
  format must define `missing_field`, and `Sqlite.RowEncoding` doesn't, so any
  record row fails `roc check`. Here the `RowEncoding` implements the whole
  documented parser protocol, and an example with record rows runs in CI on
  both compilers.
- Smaller ones will come too. roc-signals wraps its state until
  roc-lang/roc#12953 is fixed, and basic-webserver's exit code is `I64` to work
  around a glue sizing bug. Each gets a workaround commented with its upstream
  issue, as AGENTS.md asks.

## Testing

- **Processes, pure:** Roc `expect`s feed `step` events and check its effects
  (`Started` gives one `Connect`, `Disconnected` a backoff timer), with fixtures
  from recorded Paseo traffic, as `providers/paseo` does today. No host is
  involved.
- **Host integration (Zig):** a test app over real sockets covers keep-alive,
  limits, timeouts, `503` at saturation, SSE resume, slow readers, mailbox
  backpressure, budget refusals and crash exit. Live allocations must return to
  zero after each test, as roc-signals' spec host checks.
- **Load against a fake Paseo:** a scripted WebSocket server emits timeline
  events while 1, 6 and 50 subscribers watch. The test measures latency, Paseo
  connections, RSS and CPU on both platforms, and the numbers feed liton's
  benchmarks (vision.md).
- **Fuzzing:** Zig's fuzzer (`zig build test --fuzz`) runs on the HTTP, WebSocket
  and SSE parsers, and roc-fuzz (in `vendor/`) on the Roc decoders.
